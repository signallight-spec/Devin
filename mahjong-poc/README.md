# mahjong-poc — 手出し/ツモ切り検出PoC

眼鏡型デバイス用アプリの事前検証: 麻雀動画から「各捨牌が手出しかツモ切りか」を検出・記録し、可視化するパイプライン。

## 方式

1. **捨てイベント検出** (`pipeline3.py`)
   - 河(R_POND)に手がかぶさる区間 = 肌色画素のスパイク
   - 区間前後で河の牌面積が閾値以上増加 → 捨てと判定
   - 増加分の帰属は次の手入れ開始までに限る（連続する捨てで借りた増加分は、手牌差分が内部消失を示す場合のみ採用）
2. **プレイヤー帰属**
   - 俯瞰映像(`sample2`プロファイル): 捨て前後の河差分で新しく置かれた牌の重心を取り、最寄りの席別アンカーに投票（席ごとの捨牌セクターが分かれているため）。牌が手に隠れて検出できない場合はフォールバック: 各フレームで河に最も深く食い込んだ肌色成分がパネルの最寄り辺で投票（捨てた人の腕は卓中央まで届く一方、休んでいる手は縁に留まるため、深さ重み付きの票数で勝つ）
   - 肩越し映像(デフォルト): 河中の肌色連結成分が画面のどの辺から出ているかで投票: 下辺・右辺下部→手前(self)、右辺上部(高さ<400px)→右側、上辺・左辺→対面
   - 複数の手が同時に河中にある場合は各成分が投票
   - 手前以外のイベントは `opp`（判別不可の意味。相手の列は帯の外なので差分が誤判定を起こすため判別を行わない）
3. **手出し/ツモ切り判定**（手前プレイヤーのイベントのみ）
   - 捨ての前後で、手が写っていないクリーンフレームの手牌列を差分比較（±60pxアライメント、肌色画素は除外）
   - 列の縦位置は局ごとに動くため、垂直シーム(|dI/dx|)エネルギー最大の45px窓を適応探索し、150px以内のブロックを連結して列のx範囲を検出
   - 列の内部から牌が消えた → 手出し
   - 列に変化なし → ツモ切り（ツモ牌が列に入らずそのまま河へ）
   - 列右端のみ変化 → ツモ牌を右端に置く流儀の可能性（`tsumogiri?`）
   - 変化が検出列と重ならない（河・メルド等）は手出しと見なさない
4. **可視化** (`annotate.py`)
   - 6×3 の捨牌表を席別に表示。デフォルトは画面左に縦積み（対面/右側/手前）、俯瞰動画は顔カメラ領域に席レイアウトを模して菱形配置（対面=上、左=左、右=右、手前=下）。捨て順にマスを塗る: 赤T=手出し、青M=ツモ切り、灰?=相手・不明の捨て（判別不可）
   - 実位置への重畳はしない（眼鏡HUD想定の論理表示）
   - 局切り替えで表をクリア: 肩越し映像は河中の手の長時間エピソード（配牌スイープ）、俯瞰映像は全自動卓が牌を回収する際に壁4面の黄色占有率が同時に0になる区間を検出

## 結果

**検証動画1 (肩越し三人麻雀)**: YouTube「【三人麻雀 福岡 4K】手牌が見やすい麻雀動画」
- 捨てイベント 18件 → 手前 11件（手出し 5 / ツモ切り 4 / ツモ切り? 2）、対面 2件、右側 4件、帰属不明 1件
- 帰属の確認結果: 対面=上辺から腕、右側=右辺からの水平リーチ、手前=下辺/右下隅。従来手出しだった 326.7s/509.7s は相手の捨てに手前列の偶然変化が載った誤帰属だったことが判明し除去された（509.7s は証拠が弱く脱落）

**検証動画2 (俯瞰四人麻雀・分割画面)**: YouTube `nCVX7izagtg` の 24:00-30:00 区間（左=卓全体俯瞰、右下=手前プレイヤーの手牌アップ）
- 捨てイベント 38件 → 手前 10件（手出し 8 / ツモ切り 2）、対面 9件、右側 14件、左側 5件、不明 0件（308秒のツモあがり演出は一過性スパイクとして除外）
- 帰属はセクター投票（新牌の落下位置→最寄りアンカー）または最深腕のフォールバックで全件に席を割当
- 局切り替え検出: t≈312-360s で壁が全消灯 → 表を正しくクリア
- 注意: この動画では相手の席の捨牌が卓中央ではなく各自の河セクターに置かれるため、セクター投票が効く。眼鏡POVでは別ロジックが要る可能性が高い

## 使い方

依存: `pip install opencv-python numpy`。検証動画はリポジトリに含まないため、
同じ結果を再現するには該当動画を `videos/sample1_x264.mp4` として配置してから実行する。

探索スクリプトの追加依存: `mp_test.py` は `pip install mediapipe` が必要で、
初回実行時に `hand_landmarker.task` モデル（約7MB）をスクリプトと同じディレクトリにダウンロードする。

```bash
python3 pipeline3.py <video.mp4>   # results/<動画名>/ に log3.json, log3.meta.json, events.json, events3/*.png を生成
python3 annotate.py <video.mp4>    # results/<動画名>/annotated.mp4 を生成（log3.meta.json が動画と一致しない場合は中断）
```

ROI座標（R_POND, R_HAND）は1280x720の各動画専用。`PROFILES` に動画ベース名でプロファイルを登録すると自動適用される（sample2=俯瞰分割画面）。未登録の動画はデフォルト（肩越し三人麻雀動画）の座標を使う。別動画では再設定が必要。

## 既知の限界

- 肩越し/俯瞰の固定カメラ前提。眼鏡POVの手ブレ・移動視点は未検証
- 相手の手出し/ツモ切り判別は未実装 — 相手の列は裏向き＋遠距離で、枠外からの帯差分では見えない（対面の牌裏列の変化を追う別手段が必要）
- 帰属投票が混雑するイベント（複数の手が同時に河中、例: 210.5s/512.1s）は手前優先で処理
- 俯瞰動画の帰属フォールバック（最深腕投票）は、休み手がたまたま深く入る場合に誤りうる
- 帰属不能なイベント（河中の手が画面辺に繋がらない、例: 544.1s）は「unknown」表に入る
- `annotated.mp4` はフレーム書き出しのみで音声なし（実況音声を残す場合は ffmpeg で音声トラックを合成する）
- 「ツモ牌を列右端に置いて切る」ケースは右端変化で区別がつかず `tsumogiri?` になる（要ツモ牌位置追跡）
- 副露列の上部が帯にかぶる場合、メルド変化を手出しと誤ることがある
- 捨て直前まで腕が列上に残るイベントは差分が肌色マスクで潰れ、弱い変化を拾えないことがある（512.1sは行自体は不変=ツモ切りだが、腕覆い下では未検証の変化も起こりうる）
- 配牌・連荘の整理中は列全体が動くため手出し寄りになる（文脈イベント）
- 差分は「内部で牌が消えた」ではなく「内部が変化した」を見るため、ツモ切りに伴う手牌整理が内部変化を起こすと手出しと誤りうる（実データでは手出し時の整理も同じ見え方になるため現状は区別していない）。帰属を相手に振った後の手前列はこの誤判定の影響を受けない
